# Reviewed workforce attempt recovery

An invitation and its original appointment retain their full immutable history. Authentication attempts last at most five minutes. A failed/expired attempt may be replaced only while Identity returns a current qualified projection and the requesting browser supplies a fresh native OIDC request for that exact client. Person, policy, contact, issuer/OPS, provider subject and logout epoch remain unchanged. An exact qualified release may change its source/image/configuration, but cannot extend the original invitation. Cancelled/completed roots and changed epochs are never revived.

Migration010 adds append-only restart intents, attempts, pre-create challenge associations, observed provider IDs and confirmed retirement evidence. Original migrations001–009, root appointment rows, ceremony/profile records and their checksums are retained. The migration is included in the existing runner and standalone artifact packaging. Credentials, product roles and ordinary login admission are not supplied by this journal.

Before any new start or restart, Login reads the immutable enrollment outcome from Identity through a separate empty-body read-only endpoint. Completed/retired outcomes, changed Person/subject and uncertain reads cannot become pending by guessing. The outcome is read again after native retirement and before Session creation, covering a lost canonical-completion response.

Restart first reserves a unique successor intent and retires prior challenges locally. Known sessions and claimed unbound creations use a complete bounded native metadata/subject/OPS readback. Duplicate/truncated/mismatched results fail. An absent unbound creation remains pending; a fresh session must not be created by guessing that the previous call failed. An observed exact Session ID is stored before deletion, followed by actual absence confirmation. Lost deletion responses can therefore be inspected on retry without recreating a provider account/session. Only when all prior challenges have matching retirement evidence can one successor attempt activate. The qualified invitation and OIDC request are read again before activation. A paused/unknown intent does not become admission.

Challenge reservation holds contact, enrollment and epoch locks and associates custody before any provider create call. Successor cookies bind exact creation/expiry timestamps; old request/challenge/cookie/code/callback material cannot attach to the new attempt. Verification rechecks current ownership and native OTP evidence before canonical linking through Identity. Source/runtime succession itself is not credential proof.

Send quotas remain common to profile verification and Session OTP across clients and attempts: 60 seconds and three per ten minutes. The five profile-verification attempts and five enrollment OTP attempts retain their counts across restart/resend. An old profile delivery cannot be silently reused under a new browser attempt. A known accepted/unclaimed delivery may acquire an explicit replacement subject to the same quota; an uncertain native-send claim remains held. The already verified native profile may be read back; no verification flag is synthesized.

No visual composition/copy is changed in this slice. Existing French/English entry, explicit start and OTP states remain. A restart still needs a newly created owning OIDC request, never renewal of the expired one by page inspection. Source tests mock provider reads and use disposable synthetic PostgreSQL only. Release artifact, actual database rehearsal, GitOps rollout, native Mailjet/ZITADEL and authorized human proof remain separate required gates.
